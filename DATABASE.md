# Music Service — Database Documentation

Документация по схеме базы данных музыкального сервиса.

---

## 1. Обзор

| Параметр | Значение |
|----------|----------|
| **СУБД** | PostgreSQL 16+ |
| **Схема** | `music` |
| **Расширения** | `citext`, `pgcrypto`, `pg_trgm` |
| **Таблиц** | 12 |
| **Связей 1:N** | 9 |

### Назначение

БД хранит **метаданные** музыкального сервиса:

- пользователей;
- артистов;
- альбомы и треки;
- плейлисты;
- историю прослушиваний;
- лайки;
- подписки на артистов;
- устройства.

**Аудиофайлы хранятся не в БД**, а в MinIO (S3-совместимое хранилище). В БД — только **путь к объекту** (`tracks.audio_url`).

# Таблицы базы данных музыкального сервиса

---

## 👤 Пользователи и артисты

| Таблица | За что отвечает |
|---------|-----------------|
| **`users`** | Аккаунты пользователей. Хранит email, хеш пароля, имя, страну, настройки (JSONB), даты создания/обновления. |
| **`artists`** | Исполнители. Хранит имя, био, страну, фото, соцсети. Поле `created_by_user_id` — кто добавил артиста в систему. |

## 🎵 Каталог музыки

| Таблица | За что отвечает |
|---------|-----------------|
| **`genres`** | Справочник жанров (Pop, Rock, Jazz...). |
| **`albums`** | Альбомы артистов. Привязаны к `artists`. Могут быть `album`, `single`, `ep`, `compilation`. |
| **`tracks`** | Треки. Главная таблица каталога. Привязаны к артисту (обязательно) и альбому (опционально). Хранит название, длительность, путь к аудиофайлу в MinIO, битрейт, счётчик прослушиваний. |

## 📂 Пользовательский контент

| Таблица | За что отвечает |
|---------|-----------------|
| **`playlists`** | Плейлисты пользователей. Название, описание, обложка, флаг приватности, счётчик треков. |
| **`playlist_tracks`** | Связь треков с плейлистами (M:N). Хранит порядок (`position`) и дату добавления. |
| **`likes`** | Лайки треков пользователями (M:N). |
| **`artist_followers`** | Подписки пользователей на артистов (M:N). |

## 📊 Активность и статистика

| Таблица | За что отвечает |
|---------|-----------------|
| **`plays`** | События прослушиваний. Кто, что, когда, сколько секунд, с какого устройства. Источник для аналитики и рекомендаций. |
| **`listening_history`** | Агрегированная история: сколько раз пользователь слушал трек и когда в последний раз. Используется для страницы «Недавно слушал». |
| **`devices`** | Устройства пользователей (mobile, desktop, web, tv, car). Хранит ОС, версию приложения, push-токен. |

## 📻 Групповое прослушивание (Комнаты)

| Таблица | За что отвечает |
|---------|-----------------|
| **`listening_rooms`** | Комнаты совместного прослушивания. Хранит ведущего (`host_user_id`), код приглашения, статус, текущий трек, позицию, состояние паузы, управляющего (`controller_user_id`) и время последней синхронизации. |
| **`room_participants`** | Участники комнат (M:N). Роль (`host`/`guest`), время входа/выхода. Определяет, кто следующий станет ведущим. |
| **`room_queue`** | Очередь треков в комнате. Порядок, статус (`queued`/`playing`/`played`/`skipped`), кто добавил. |
| **`room_play_history`** | Архив проигранных в комнате треков. Сколько играло, дослушали ли до конца. |

---

## 💡 Ключевые принципы работы БД

- **Аудиофайлы** хранятся в **MinIO**, а в БД лежит только путь (`tracks.audio_url`).
- **Пароли** хранятся в виде хешей (BCrypt/Argon2), не в открытом виде.
- **Денормализация:** `tracks.play_count`, `playlists.track_count`, `listening_rooms.host_user_id` дублируют вычисляемые данные для скорости. Обновляются вручную из backend.
- **Без триггеров:** вся логика (счётчики, `updated_at`, передача host'а) реализована в коде C#.
- **Без партиционирования:** таблица `plays` — обычная, для учебного проекта этого достаточно.
